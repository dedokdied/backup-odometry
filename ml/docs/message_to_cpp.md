## 1. target_a_residual на движении — это шум, а не сигнал (главное)

Прогнал `target_a_residual vs t` по `bcc9e7a2` на участке v > 5 км/ч. Вот первые
5 значений:

```
t=1786352408.52  v=1.401 м/с (5.0 км/ч)  a_model=+2.2000  target=-3.74358
t=1786352408.55  v=1.473 м/с (5.3 км/ч)  a_model=+2.2000  target=-2.66868
t=1786352408.57  v=1.558 м/с (5.6 км/ч)  a_model=+2.2000  target=-1.50803
t=1786352408.92  v=1.644 м/с (5.9 км/ч)  a_model=+2.2001  target=-1.34449
t=1786352408.95  v=1.620 м/с (5.8 км/ч)  a_model=+2.2002  target=-2.58285
```

Два наблюдения:

**`a_model` зажат на ровно +2.2000 м/с²** на протяжении выборки. Похоже на
clamp в физической модели — она упирается в потолок и перестаёт различать
режимы. Если модель насыщается, корректор не получает полезного признака.

**`target_a_residual` скачет с −3.74 до −1.51 за 60 мс.** Складывая с
`a_model = 2.2`, получаем подразумеваемое истинное ускорение −1.54 → +0.69 м/с²
за 60 мс. Для трамвая это физически невозможно: любая разумная модель
разгона ограничена ~1.3 м/с², и скачок на 2.2 м/с² за 3 отсчёта невозможен при
любом ограничении на jerk.

Статистика по движению: std **1.41 м/с²**, диапазон −3.74 … +4.14, 21.8% всех
строк вне ±1.50.

Отсюда главное: **корректор не может обучиться предсказывать цель, у которой шум
больше сигнала.** Поэтому одного количества данных не хватит — нужно сначала
починить цель. Проверь у себя, как считается `a_true`: если это численное
дифференцирование колесной скорости, там будет ровно такой шум. Моя версия
GNSS-производной со сглаживанием 1 с даёт std 0.562 — на порядок спокойнее.

Стоянка при этом в порядке: RMSE 0.330 против baseline 0.562, модель там работает
и gain положительный (0.59).

## 3. Баг в validate_artifact.py

Валидатор у меня падает с

```
ERROR: feature count 16 != 0
ERROR: outputs ['a_residual', 'log_scale', 'mu'] != []
REJECTED
```

Причина — парсер, а не артефакт. Он печатает `features (16) : []`, то есть
извлекает пустой массив. В его заголовке на строке 4 есть комментарий
`// kFeatureNames / kOutputNames arrays below and rejects any model artifact`,
и парсер делает:

```python
i = text.find(marker)   # первое вхождение подстроки
j = text.find("{", i)
k = text.find("};", j)
```

Первое вхождение `kFeatureNames` — это комментарий на строке 4, поэтому `{`
ищется со строки 20, а `};` закрывается на строке 46. В блоке 20–46 нет ни
одного строкового литерала → `[]`. Настоящий массив объявлен на строке 49.

Фикс — привязаться к объявлению, а не к подстроке:

```python
m = re.search(marker + r"\[[^\]]*\]\s*=\s*\{", text)
j = m.end() - 1
```

С этой привязкой корректно извлекается `['u', 'v', 'a_model', 'grade', ...]`.

`kNumFeatures` / `kOutputNames` / `kFeatureSchemaVersion` у тебя работают,
потому что там `re.search` с `\s*=\s*(\d+)`, и комментарий их не задевает —
именно поэтому расхождение выглядит так странно: счётчики верные, имена пустые.

Файл `ml_features.hpp` я не правил — он в твоей ветке, менять молча не стал.
